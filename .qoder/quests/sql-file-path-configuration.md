# SQL 文件路径配置功能优化设计文档

## 1. 问题描述

当前 SQL 文件路径配置功能中的文件夹选择机制存在严重用户体验问题。当用户点击"浏览"按钮选择文件夹时，系统不会直接弹出文件夹选择窗口，而是会在任务栏生成一个虚拟任务，用户需要先选择该任务，再进行二次点击才能在浏览器中显示资源文件管理器的文件夹选择界面。

这个问题影响了用户的操作流畅性，不符合用户对直接交互的预期，亟需重新设计实现。

## 2. 设计目标

1. 实现文件夹选择功能的直接响应机制
2. 提供一致且符合用户预期的操作体验
3. 保持系统的稳定性和兼容性
4. 确保在各种环境下都能正常工作

## 3. 当前实现分析

### 3.1 前端实现

- 使用 JavaScript 的 fetch API 向后端发送请求
- 请求地址为`/system/select-folder/`
- 接收 JSON 响应并更新输入框值或显示错误信息

### 3.2 后端实现

- 使用 Windows API (ctypes 调用 shell32.SHBrowseForFolderW)实现原生文件夹选择对话框
- 当 Windows API 失败时，回退到 tkinter 实现的文件夹选择对话框
- 返回 JSON 格式的结果给前端

### 3.3 问题根源

当前实现通过 HTTP 请求触发文件夹选择对话框，这种方式会打断用户操作的连续性，导致操作系统将对话框视为后台任务处理，从而产生任务栏虚拟任务而非直接弹出窗口。

## 4. 解决方案设计

### 4.1 总体思路

采用前端直接触发本地资源访问的方式替代后端触发，利用现代浏览器提供的本地文件系统 API 或者 HTML 原生能力来实现文件夹选择功能。

### 4.2 技术选型

1. **首选方案**: HTML `<input type="file" webkitdirectory>` 元素

   - 利用浏览器内置的文件夹选择能力
   - 直接在浏览器上下文中弹出选择对话框
   - 兼容性好，支持主流现代浏览器

2. **备选方案**: File System Access API
   - 提供更丰富的本地文件系统访问能力
   - 用户体验更好，但浏览器支持度有限

### 4.3 实现架构调整

#### 4.3.1 前端重构

- 移除通过 AJAX 请求后端触发文件夹选择的机制
- 引入隐藏的`<input type="file" webkitdirectory>`元素
- 通过 JavaScript 程序化触发 input 元素的 click 事件
- 监听 input 元素的 change 事件获取用户选择的文件夹路径
- 更新路径输入框的值

#### 4.3.2 后端调整

- 移除与文件夹选择相关的复杂实现（Windows API 和 tkinter）
- 保留路径验证逻辑以确保输入的有效性

## 5. 详细设计方案

### 5.1 前端实现细节

#### 5.1.1 HTML 结构调整

```html
<!-- 添加隐藏的文件夹选择输入元素 -->
<input type="file" id="folderSelector" webkitdirectory directory style="display: none;" />
```

#### 5.1.2 JavaScript 逻辑重构

```javascript
// 新增文件夹选择函数
function selectFolder() {
  const folderSelector = document.getElementById("folderSelector");
  folderSelector.click();
}

// 新增文件夹选择监听器
document.getElementById("folderSelector").addEventListener("change", function (event) {
  const files = event.target.files;
  if (files.length > 0) {
    // 获取文件夹路径
    const folderPath = files[0].webkitRelativePath.split("/")[0];
    // 在实际应用中，我们需要获取完整的文件夹路径而不是相对路径
    // 这里需要特殊处理
    document.getElementById("sql_output_path").value = getDirectoryPath(files[0]);
  }
});

// 辅助函数：从文件对象中提取目录路径
function getDirectoryPath(file) {
  // 对于webkitdirectory，我们需要特殊方法获取真实路径
  // 此处为示意实现，实际可能需要根据浏览器差异调整
  return file.path || extractDirectoryFromWebkitPath(file.webkitRelativePath);
}
```

#### 5.1.3 兼容性处理

考虑到`webkitdirectory`属性的浏览器兼容性，需要提供降级方案：

- 对不支持该属性的浏览器，显示提示信息建议用户手动输入路径
- 或者保留原有 AJAX 方式作为最后的备选方案

### 5.2 后端实现调整

#### 5.2.1 移除复杂文件夹选择逻辑

删除现有的基于 Windows API 和 tkinter 的文件夹选择实现，简化代码结构。

#### 5.2.2 保留核心验证逻辑

继续保留路径有效性验证、权限检查等核心功能，确保系统的安全性。

## 6. 用户体验优化

### 6.1 操作流程改进

1. 用户点击"浏览"按钮
2. 系统立即在当前浏览器上下文中弹出系统原生文件夹选择对话框
3. 用户选择文件夹后，对话框自动关闭
4. 路径输入框自动填充所选文件夹路径
5. 用户可继续完成其他配置项并保存

### 6.2 错误处理机制

- 当浏览器不支持相关特性时，提供清晰的用户引导说明
- 保持原有的手动输入路径功能作为兜底方案
- 增强路径验证的提示信息，帮助用户快速定位问题

## 7. 安全性和兼容性考虑

### 7.1 安全性

- 继续保留服务端路径验证逻辑，防止恶意路径注入
- 限制只能选择文件夹，不能选择文件
- 验证路径是否具有写入权限

### 7.2 兼容性

- 主流现代浏览器（Chrome、Edge、Firefox）均支持`webkitdirectory`属性
- 对老旧浏览器提供优雅降级方案
- 在企业环境中常见的浏览器版本上测试功能可用性
